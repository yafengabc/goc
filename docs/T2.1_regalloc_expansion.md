## 2. 设计方向

### 2.1 目标变量（两类）
1. **参数**：函数序言里溢出（mov [rbp-N], rcx/rdx/r8/r9）后反复重载——每处「溢出+重载」改寄存器直读省 1-2 条。
   注意 bench2 的 bsort 把数组基址 `a` 当作参数反复重载（7 次在循环内）——**数组/指针参数**是最大单项。
2. **无 call 内层循环里的高频局部变量与临时量**：寄存器分配只在「无调用点」的区域内跨基本块存活才值得；
   跨 call 必须保守写回。

### 2.2 与现有 varInfo.reg（静态寄存器分配）的整合
- 现状：局部变量被静态分配到 callee-save 寄存器（rbx/r12-r14），条件是 intClass && !addrTaken && 有空闲寄存器。
- 扩面：**把参数纳入同一套分配**（参数也是变量实体），并放宽为「区域内分配」：
  - 函数内做一次简单活性/调用点分析：把函数体按 call 分割成无调用区域；
  - 参数与局部变量若在其整个活跃区（首次定义到最后一次使用）内不跨越任何 call，则全程驻寄存器（无需写回）；
  - 若活跃区跨越 call：callee-save 寄存器可全程驻留（调用点自动保存），但前提是 call 边界处值一致性——
    保守策略：跨 call 的寄存器变量在 call 前写回槽、call 后重载（这就是「保守写回」）。
- 寄存器池：caller-save（r8-r11 等）只能用于无 call 区域；callee-save（rbx/r12-r14）可跨 call。
- 参数入口：参数从 ABI 寄存器进来，可直接留驻分配的寄存器（省去序言溢出），无 call 时零开销。

### 2.3 关键工程点
- **槽位保留**：即使变量驻寄存器，仍保留其栈槽（用于：跨 call 写回、addr-taken 间接写、调试一致性）。
  这避免语义变化：任何写到槽的路径（如 `*p = x` 经指针写 x）不会破坏寄存器镜像——**必须检查 addr-taken
  变量的写穿透**：如果变量 addr-taken（可被指针写），则不能安全驻寄存器（现状分配已排除 addrTaken）。
- **loadVar/storeVar 改造**：vi.reg 已有静态分配路径（mov rax, r12 / mov r12, rax），扩面只是更多变量命中。
- **活跃性数据**：liveness.go 已有 def/use 计算，可复用做区域分析。
- **与 T1.6 的交互**：T1.6 落地后，int 寄存器缓存变量持物化值（低 32 有效），inc/dec 用 32 位形式——
  扩面后的寄存器变量自动继承该约定；指针型参数（char*/void*）驻寄存器时全宽。
- **跨 call 写回成本**：若写回过于频繁（每次 call 前 mov [rbp-N], r12 + 每次 call 后 mov r12, [rbp-N]），
  可能不如直接走槽——写回决策需要与「槽缓存转发」pass 对拍。

## 2.5 R2/R3 实测结论（2026-10-03，含两次走错的弯路）

**最终形态**：局部变量**优先**分配（保持原顺序），参数只吃**剩余**寄存器；
leaf 函数（AST 无 call 且无聚合数据）的池额外加 r8/r9。

### 2.5.1 弯路一：参数优先 = 负收益（-O1 净 +1，-Os 净 +218）

第一版让参数**先**于局部变量挑寄存器。局部变量于是被挤到栈上，而**溢出的局部
变量远比溢出的参数贵**：goclib `fmt_int_part` 的循环计数器从 `dec r13d` 变成
load → `dec` → store → reload，**每次迭代多 3 条内存往返**，完全吃掉参数省下的
reload。函数级分解证实罪魁是 goclib 的格式化函数：`vfmt` +42、`fmt_int_part` +8。

顺带否掉"把阈值调大"这条 intuition：语句数阈值 4 → 净 0，12 → +208，30 → +214，
**越大越差**（更多中等大小函数被参数寄存器化，内联被破坏，而内联比省 reload 值钱）。

### 2.5.2 弯路二：只判「AST 无 call」不够 —— codegen 会自己发 call

加上 r8/r9 后 10 个例子 `0xC0000005`（访问违例）。原因：**codegen 会为聚合数据
自动降级出 call**——`genBraceInit` / `copyBytes` 对大数组/结构体拷贝与清零会
`emitCall("memcpy")` / `emitCall("memset")`（codegen.go:7339/7549），AST 里**没有
Call 节点**，而 Win64 的 memcpy/memset 第 3/4 参数就在 r8/r9。

修法：池扩展额外要求 `!hasAgg`（函数不声明/不接收数组、struct、union、_BitInt）。
这砍掉了 goclib 大量格式化函数（它们到处是 `char t[20]` 缓冲），收益因此从
-860 降到 -215——**宁可少赚，不可错发**。

### 2.5.3 收益（-O1，bench2/goclib/mathlib/stress 合计）

| 阶段 | 指令行 | 相对 C5 |
|---|---|---|
| C5 基线 | 47577 | — |
| 参数优先（错） | 47578 | +1 |
| + r8/r9 扩池，AST 判 call（错，10 例崩溃） | 46717 | -860 |
| **最终：局部优先 + 排除聚合** | **47362** | **-215** |

### 2.5.4 为什么 r8/r9 而不包含 r10/r11

codegen 把 r10/r11 当 scratch 硬编码（分别 45 / 19 处 emit：genBinary 的操作数
spill、genCall 的实参、索引的 `movsxd r11`）。局部变量住进去会被任何算术表达式
 shred 掉。rbx/r12-r14 + r8/r9 是仅存的 6 个"goc 从不主动用作 scratch"的寄存器。

### 2.5.5 与内联的互斥（保留约束）

`extractInlineCand` 的安全屏幕有一条 `calleeSaveWrites[operands[0]]` → 拒绝内联
任何写 callee-save 的函数体。所以**参数/局部变量一旦 callee-save 化，函数就失去
可内联性**。R2 因此跳过"被调用的小 leaf"（`t21InlineLikely`：无 call + ≤4 条语句
+ 在调用图中）。注意这条只挡 callee-save；r8/r9 理论上可内联，但让内联体去 clobber
调用方的 caller-save 值需要另加论证，本次不做。
