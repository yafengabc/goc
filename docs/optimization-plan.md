> 版本：2026-10-02（10-02 评审修订：校正"纯栈式/无 CFG"误判、补 T1.6 符号扩展消除、压低 Tier 1 运行预期、T1.1 内部档重编号、更新回归基线） · 状态：方案（待评审） · 适用范围：`src/` 代码生成与优化管线  
> 配套实测：`bench/optprobe.c`、`bench/bench2.c`（探针与基准程序，见文末）

## 1. 现状盘点（实测，2026-10-02）

### 1.1 优化管线全景

goc 是**单趟架构**：`parser → AST → check → codegen`，codegen 直接产出汇编文本行  
（`Inst[]` 线性指令流），**无类型化中间表示（IR）、无 SSA**。但初稿"纯栈式、无寄存器  
分配、无 CFG"的判定须校正——下面两条是**已存在**的事实（非待建），T2.1/T2.3 应视为"扩展/升级"而非"从零新建"：

- **已有静态寄存器分配**：`codegen.go` 对普通 `int` 局部变量按声明顺序分配 callee-save 寄存器（`varInfo.reg` + `regPool`，`calleeSaveAll=[rbx,r12,r13,r14]`；`codegen_test.go` 断言"超过 4 个 int 局部必分配"）。取地址 / 数组 / `double` 局部与**所有参数、临时量**仍落栈槽 `[rbp-N]`，故"所有局部变量一律驻留栈槽"不成立。
- **已有轻量 CFG（liveness 段模型）**：`liveness.go` 已做基本块段切分 + 槽活跃分析，服务于 `livenessDSE`；非完整 CFG（缺 succ/pred/loop）。

综上，运算形态对**参数 / 临时量 / 非 int 局部**仍是 **load → op → store** 三段式；int 局部已寄存器化（见上）。

`Gen()`（`src/codegen.go` 的 `if c.opt >= 1` 优化块，现位于 :2542 附近，行号随代码增长）：

```
opt >= 1:
    opt != 2 时  inlineCalls   —— 叶函数内联（唯一会"增长"程序的 pass）
    constProp                  —— 线性前向值跟踪（regs/imms 两张表，label/内联 asm 全清）
    peepholeIR                 —— 单/双窗口窥孔（mov $0→xor、store→load 短路、slot knowledge）
    deadStores                 —— 全宽 store 重写前的小宽度 store 删除
    livenessDSE                —— 基本块段活跃分析驱动的死代码/死存储消除
opt == 0:  文本级窥孔（legacy，逐字节保持历史输出）
```

已存在的基础设施可复用：`liveness.go` 已做基本块段切分（segments）与槽活跃分析；  
`constProp` 已有值跟踪器骨架；`peepholeIR` 已有 slot knowledge 窗口；`inlineCalls`  
已有函数形状提取与展开模板。

### 1.3 栈式 codegen 的膨胀模式（根因）

以 `fib(n-1)` 递归调用为例（`-O1` 输出片段）：

```
mov rax, [rbp-48]      ; 读参数 n
mov [rbp-64], rax      ; 存临时槽
mov rax, 1
mov r10, [rbp-64]
sub r10, rax           ; n-1
mov rax, r10
shl rax, 32            ; int 符号扩展
sar rax, 32
mov [rbp-64], rax
sub rsp, 32            ; shadow space
mov rcx, [rbp-64]      ; 参数入寄存器
call fib
add rsp, 32
mov [rbp-56], rax      ; 返回值入槽
```

一次 `fib(n-1)` 调用 = **14 条指令**；一个 `n < 2` 比较 = **6 条指令**（参数入槽、  
读槽、入临时槽、载常量、读临时槽、cmp）。

**比内存搬运更致命的隐藏杀手——符号扩展膨胀**：上面 `fib(n-1)` 片段里每条 `int` 运算结果后都紧跟 `shl rax,32; sar rax,32`——goc 把 `int` 建模为 32 位、在 64 位寄存器里反复回绕符号扩展，每条算术指令额外背上 2 条移位。**这极可能是对标 gcc 那 10× 差距的头号单项杀手，比 load/store 流量更致命**，但初稿把它漏出了优化目标清单（已补为 §3 **T1.6**）。内存搬运是第二大来源，两者共同构成 10× 差距主体。

---

> **设计决策：暂不引入 SSA。**
> goc 当前为单趟 codegen + 线性 `Inst[]`，已具备轻量 CFG（`liveness.go` 的 `lvBlock`，带
> `succ` 边）与活跃区间。本方案的 Tier 1-2（符号扩展消除、槽缓存、局部寄存器缓存）均为局部或
> CFG 级优化，**不需要 SSA**；全局值编号可用基于哈希的 value numbering 跑在 CFG 上、寄存器分配
> 可用线性扫描/区间着色（直接吃现有活跃区间），均不依赖 SSA。引入 SSA 须先用带类型 IR 替换
> `Inst[]`、再建真 CFG、再做 SSA 构造/销毁与对应 codegen——本质是后端重写，对 goc 的 C 子集
> 规模与目标不成比例。仅当进入 Tier 3 后撞到具体墙（如 spill 劣化、全局 CSE 做不动）且 SSA 能
> 明确解决时再回看。

## 2. 设计原则与硬约束

1. **正确性绝对优先**：所有 pass 默认保守。无别名分析前，只优化精确栈槽  
   `[rbp-N]` 的已知形态；指针/数组间接访问、`&x` 取址、内联 `__asm` 一律失效。
2. **flag 语义不动**：`cmp/test` 写 flags 不参与重写；`foldALU` 只记录不删除指令的  
   既有保守策略延续（除非新 pass 显式证明不跨条件码边界）。
3. **内联 `__asm` 是禁区**：任何 pass 遇 `instRaw` 行必须断开窗口/清空知识  
   （`peepholeIR`/`constProp`/`livenessDSE` 已遵守，新 pass 沿用）。
4. **回归基线不回退**：当前 HEAD 基线约 **462-463 pass / 0-1 fail**（作者声 463/0；本沙箱内因 linux 腿产物读拦截为 460/3，环境性、非回退），唯一预存 fail 为 TestOsKeepsCalls（非本方案引入）。数字须随 HEAD 重测、勿硬编码。  
   `go test ./src` + `./src/goa` 全绿必须保持。
5. **逐级验收**：每个 pass 独立可开关、有单元测试（沿用 `codegen_test.go` /  
   `liveness_test.go` 风格）、与 gcc 对拍输出一致。
6. **工程约束**：无 go.mod、纯标准库；`codegen.go` 已是 276KB 巨文件——新 pass  
   独立成文件（如 `src/opt.go`、`src/cfg.go`），不继续膨胀单文件。

## 3. 优化路线（三梯队）

### Tier 1 — 快赢（P0，预计 2-4 天）

| #    | 优化项                       | 原理                                                                                                                                                  | 实施点                                                          | 预期收益                          | 风险                       |
| ---- | ------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------ | ----------------------------- | ------------------------ |
| T1.1 | **优化级别真实分层**              | `-O1/-O2/-O3` 语义化：-O1=现有全套；-O2=+常量折叠增强；-O3=+强度削减/寄存器缓存（随 Tier2 挂载）。**注意**：区分 -O2/-O3 需新内部档，但内部 `2` 已被 `-Os`（size-first）占用，须重编号（建议 -O1→1 / -O2→3 / -O3→4 / -Ofast→4 / -Os→2 不变）                                                                                  | `main.go` `optFromSuffix()`（:306，行号漂移按名检索）；`codegen.go` Gen() 的 `if c.opt>=1` 块（:2542） | 产品语义正确；为后续 pass 提供挂载点         | 低                        |
| T1.2 | **常量折叠增强（真删除）**           | 现状 constProp 只"记录"不"删除"（保 flag）。扩展：已知 reg 值的消费点直接内联 imm（不跨 flags 边界）；`mov rax,imm64` 已知 → 32 位短 imm；`mov $0` → `xor`（peephole 已覆盖）；imul 已知 → lea 序列 | `codegen.go` `constProp()`、`foldALU()`（行号随代码增长，按名检索）                 | 减少 mov/imm 流量，中等              | 中（32/64 位语义、flag 边界）     |
| T1.3 | **代数恒等**                  | `x+0 / x-0 / x*1 / x*0 → 0`、`x*2^k → lea/add`（x86 回绕语义下安全）；比较 `x==0` → 直接 test                                                                      | parser 表达式层 + codegen Binary/比较节点                            | 算术热点可观                        | 低（乘 0/1 恒等在回绕语义下安全；除法除外） |
| T1.4 | **冗余 load/store 消除（槽缓存）** | 线性扫描维护 `[rbp-N] → 值` 缓存：同槽连续 load 删第二条；`mov [s],rax; mov rcx,[s]` → `mov rcx,rax`；store 到已知同值槽删除。label/调用/内联 asm/间接写全失效                             | 新 pass（`src/opt.go`）或扩 peepholeIR（:2836）                     | **高**——栈式模型的核心流量就是 load/store | 中（保守失效集是安全关键）            |
| T1.5 | **零初始化合并**                | 数组/结构体 `.zero` 段对齐与重复零数据合并                                                                                                                          | codegen 数据段发射                                                | 小                             | 低                        |

| T1.6 | **冗余符号扩展消除（最高 ROI）** | goc 把 `int` 当 32 位、每条运算后发 `shl 32; sar 32` 回绕符号扩展（见 §1.3）。相邻 `shl32/sar32` 且中间不被 flag/宽度敏感指令消费时可安全删除；更远目标是让 int 以 64 位原生宽度承载、仅在窄存/比较/算术右移等宽度敏感点做窄化 | codegen 类型宽度标注 + 扩展 `peepholeIR` 的 value knowledge | **最高单项**——10× 差距头号杀手 | 中（须保证算术右移/比较/窄存不被误删；溢出语义） |

**Tier 1 完成后预期**：指令数下降 **25-40%**（fib/排序类，符号扩展消除 + 槽缓存贡献大头），运行耗时约 **1.5-2×** 收敛（goc -O2 ≈ 340ms → 170-230ms）。**初稿的 2-3× 偏乐观**：10× 差距不全是 load/store，还含符号扩展膨胀、参数重载、无循环优化，单靠 Tier 1 难以压到 130ms 档。

### Tier 2 — 中期杠杆（P1，预计 1-2 周）

| #    | 优化项                  | 原理                                                                                                         | 实施点                                                | 预期收益                         | 风险                               |
| ---- | -------------------- | ---------------------------------------------------------------------------------------------------------- | -------------------------------------------------- | ---------------------------- | -------------------------------- |
| T2.1 | **寄存器分配扩面（扩展现有分配器）** | 现有 `codegen.go` 已对普通 `int` 局部做静态 callee-save 分配（见 §1.1）。本项把它**扩展**到：① 函数参数（当前从入参槽反复重载）；② 高频临时量（load→op→store 的中间值）；③ 直接复用现有 prologue/epilogue 现场保存 + 取址/数组/double 强制落栈逻辑，不要重建 | 扩展 `codegen.go` 的 `regPool`/`varInfo.reg`；活跃区间仍用 liveness.go 的 segments | **最高单项之一**——补上参数/临时量寄存器化，预计再 1.5-2× | 中（函数边界、别名、跨 call 保守写回；取址/数组/double 留栈现有逻辑已覆盖） |
| T2.2 | **尾调用优化（TCO）**       | `return f(x)` → 参数重排后 `jmp f`；尾部递归热点收益大                                                                    | codegen 函数 epilogue 识别"call 后立即 ret"形状             | 递归类 2-3×                     | 中（栈参数重排、与 T2.1 交互）               |
| T2.3 | **CFG 升级（基于现有 segment）**         | liveness.go 已有基本块段切分 + 槽活跃分析（轻量 CFG），本项升级为带 succ/pred/loop 的完整 CFG：succ/pred、可达性、循环检测；为 T2.1/T2.4/T3.x 打地基                          | 新文件 `src/cfg.go`                                   | 间接（解锁后续）                     | 低                                |
| T2.4 | **分支优化**             | `jmp` 链消除（L1: jmp L2 → 目标合并）、jcc→jmp 合并、相邻块合并、不可达块删除                                                       | 基于 T2.3                                            | 中（循环体瘦身）                     | 低                                |

**Tier 2 完成后预期**：goc -O2 收敛到 gcc -O2 的 **3-4×**（340ms → 100-140ms）。

### Tier 3 — 远期（P2，按需）

| #    | 优化项                                      | 说明                                                                     |
| ---- | ---------------------------------------- | ---------------------------------------------------------------------- |
| T3.1 | **完整寄存器分配**（线性扫描/图着色）                    | 基于 CFG + 活跃区间，14 个 GP 寄存器。需处理取址变量留栈、栈溢出、跨调用。收益 5× 级                    |

## 4. 实施顺序与依赖

```
T1.1 级别分层（立即，为挂载点；注意内部档重编号，见 §6）
  ├─ T1.2 常量折叠增强 ─┐
  ├─ T1.3 代数恒等 ─────┤（互不依赖，可并行）
  ├─ T1.4 槽缓存 load/store ─┐
  └─ T1.6 符号扩展消除 ──────┘（扩展 peepholeIR，ROI 最高）
T2.3 CFG 升级（基于现有 segment）──→ T2.1 寄存器扩面 → T2.4 分支优化
T2.2 TCO（可与 T2.1 并行，需小心交互）
T3.x（按需）
```

**建议的首个落地组合**：**T1.4（槽缓存）+ T1.6（符号扩展消除）作为第一批**——两者都  
复用 constProp/peephole 的失效纪律（label/调用/内联 asm/间接写全失效），单测好写  
（store→load 与 `shl32/sar32` 形状已有测试基础），且 T1.6 的 ROI 高于 T1.4。T1.1  
级别分层可并行推进（纯映射调整，几乎零风险）。
